## 本作 CRT 辨識增補

已載入的 `runtime/tpcrt.FindDelay` 只認得兩種外層形式。本作是第三種：
ES 先設為0040h，次數先讀入 BX，每次以 CX=BX 呼叫同一個三指令內圈。
這項差異只描述原始 bytes，不據此推定精確編譯器版本。

| 欄位 | 證據 |
|---|---|
| 輸入 | `GAME.EXE` v1.10，SHA-256 `35ad635e558852925b7028a921aacafc2df8e84be24a8a1136c6267471948d69` 的正常解壓記憶體 |
| 工具與位址 | IDA Pro 9.4、16-bit；dosgolem 執行期 `1DF0:029C–02C6`，線性 `0x1E19C–0x1E1C6` |
| 辨識範圍 | 完整43 bytes；次數欄位之外逐 byte 符合，常規記憶體中與所有既有形式合計唯一 |
| 次數欄位 | 本體 `+0x16` 的 little-endian word，實際為 `FB82`；`DS=2096`，線性 `0x304E2` |
| 內圈 | 本體 `+0x23`，線性 `0x1E1BF`；`26 3A 05 75 02 E2 F9 C3` |
| 執行語意 | 同既有 TP5 形式的三指令內圈；只增辨識表，不修改 machine 的加速演算法 |
| 失配 | 無命中、任一固定 byte 不符、不同形式多重命中，均回 false |

外層 bytes：

```text
8B DC 36 8B 57 04 0B D2 74 16 B8 40 00 8E C0 33
FF 26 8A 05 8B 1E ?? ?? 8B CB E8 06 00 4A 75 F8
CA 02 00 26 3A 05 75 02 E2 F9 C3
```

原始匯出在 `workplace/probe/demo-control-v1/keywait-1df0-ida.json`，
記錄輸入切片雜湊、IDA 位址、原始 bytes 與 operand。這裡只需確認本作的呼叫形式與欄位，
不重新研究 PIT、校準迴圈或逐週期硬體時序。

## 正常前端抽樣

[固定收據](../re/021-toolbar-runtime.json)以正式程式 `1892712` 冷開機至開場標題，
每條路線 1100 格。入口為 `bash tools/toolbar-acceptance-receipt.sh <新名稱>`，
檢查器為 `tools/toolbar_acceptance_check.py`，與規格020共用同狀態對照。

- 1x 快轉開／關皆為 105875000 步。CPU、完整記憶體、原版畫面、色盤、DOS 檔案與七組截圖相同。
- 快轉開啟實際計入 67740 步，關閉為零，避免以沒有經過 Delay 的路線充作等價性證據。
- 六種倍率各有選單截圖與實際讀值。時脈為 50／100／200／400／800／1600%，每格預算為 96250 步乘設定倍率。

- 正式點擊處理會保存各倍率；互動模式重新啟動成功讀回 32x。Delay 未登記前保持實際 1x。
- 前端現有自動調節、主機過慢退回 1x、未登記 Delay 不加速及選單邊界測試通過。

本輪使用固定步數的無頭自動模式。實際耗時與繪製次數保存於收據，
不據此宣稱互動顯示達到 30 fps。互動模式的正常玩家路線與自動調節效能仍是 #14 的剩餘驗收點。

## 效能量測修正與互動驗收：READY

原程式 `cmd/pod-play/main.go` 的 `perf.draw` 記錄位於 `drawBar` 的顯示條件內，
因此只計工具列繪製；截圖額外繪製工具列也會增加次數。這是診斷數字的錯誤，
不影響遊戲輸出。前一份固定收據保留原值，不能將其 `drawfps` 解讀為完整畫面的更新頻率。

將計時移到 `game.Draw`，涵蓋合成、工具列、海報與 `screen.WritePixels`。
此耗時不包含 Ebitengine 在回呼後的 GPU 呈現；以 Draw 回呼時間間距另量更新頻率。
工具列顯示／隱藏與存截圖不得額外增加 Draw 次數。正常同輸入的遊戲狀態、原版來源與 PNG 須保持相同。

互動驗收以 `-frames 0` 冷開機、正常讀取既有存檔至街景，沿用既有玩家路線。
隔離研究副本只附加 Update／Draw 讀值，依序抽測六種設定倍率及切回1x，
保留時脈、自動調節、單格耗時、實際虛擬步數與 Draw 間距。
研究結束使用視窗關閉事件，不在正式程式增加測試退出旗標。
主機不足時應依既有策略降低實際倍率，設定倍率仍保存；不為通過量測更改遊戲時鐘或規則。

重生入口：`bash tools/speed-interactive-receipt.sh <新名稱>`。
`tools/speed_interactive_probe.py` 建立隔離讀值副本並在私人 Xvfb 送出正常關窗事件。
`tools/speed_interactive_check.py` 比對固定基準、正常讀檔狀態與來源，並彙整七段倍率量測。
每段200格，前50格供調節、後150格量測完整時間區間，包含截圖成本；
30 fps 達成與功能通過分別記錄，不修改門檻迎合結果。

2 CPU 與 4 CPU 使用相同程式作資源對照，兩批結果都保存；4 CPU 以
`POD_SPEED_CPUS=4` 選擇，預設維持2。記錄 cgroup CPU 配額與節流統計，
用於區分主機資源限制與自動調節覆蓋缺項，不改變1x預算或驗收門檻。

## 繪製間隔回饋：READY

4 CPU 的正常互動收據在第5103格，最近十個 Draw 間隔約17.52 fps，
原控制仍將時脈從50%提高至62%。cgroup沒有CPU節流。
原 `observe` 只看模擬耗時，沒有觀察畫面更新，與「30fps優先」的定案不符。
兩個修改前收據均保留：[2CPU](../re/022-speed-interactive-runtime.json)、
[4CPU](../re/022-speed-interactive-4cpu-runtime.json)。

沿用現有倍率、1x下限、CPU耗時回饋與調節間隔，在前端新增 Draw 間隔的指數平均：

- Draw 間隔高於1/30秒時降低實際時脈，直到1x下限。
- 只有 Draw 間隔不高於1/35秒，且模擬耗時低於原門檻時才提高時脈。
- 30–35fps區間保持時脈，避免反覆升降。尚無Draw間隔時沿用原CPU回饋。
- 1x與固定自動模式不採用這項回饋；原版狀態、固定步數與輸入語意保持相同。

驗收包含慢繪製／快模擬的拒絕升速、繪製恢復後再升速、遲滯區間，
以及正常讀檔至街景的六倍率、固定1x同狀態回歸。3倍HD與預設2倍分開記錄，
1x本身不足30fps時保留效能限制，不降低1x基準或宣稱達標。
